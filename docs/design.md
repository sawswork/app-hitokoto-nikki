# 設計書 — ひとこと日記(仮)

このドキュメントは実装の指針。変更したら理由とともに更新する。

## 1. コンセプト

- 1日1行書くだけで、カレンダーに思い出がたまっていく日記アプリ。
- 続けるハードルを極限まで下げる:入力は1行、開いたらすぐ書ける。
- **完全オフライン**。サーバーなし・広告なし・アカウント不要・端末内保存のみ。
- 主役は「書いた日が色づくカレンダー」。埋まっていく達成感が継続の動機。

### 差別化ポイント
- 書いた日が色づくカレンダーが主役の画面。
- 未来の日付にも書ける(予定・楽しみ・約束のメモとして)。
- 完全一致検索(入力した語をそのまま含む日記を探す)。
- テキスト書き出し(バックアップ):全日記を1つのテキストとして共有/保存。

## 2. 画面構成

アプリは主に3つの領域で構成する。ボトムナビは使わず、カレンダー中心のシンプルな導線にする。

### 2.1 カレンダー画面(ホーム・起動時に表示)
- 月表示のカレンダーが主役。日記のある日はドット/塗りで色づく。
- 上部:年月と「< 今日 >」的な移動。タップで月移動。
- 日をタップ → その日の編集画面(エディタ)へ。
- 右上:検索アイコン、メニュー(書き出し・設定・購入)。
- 今日の日付は強調。未来日も普通にタップして書ける。

### 2.2 エディタ画面(1日の日記)
- 対象日を大きく表示。1行(複数行も可)のテキスト入力。
- 保存はオート(離脱時/変更時に保存)。明示的な「保存」ボタンは置くが必須ではない。
- 空にして保存 = その日の日記を削除。
- 前日/翌日へスワイプまたは矢印で移動できると理想(初期は矢印ボタン)。

### 2.3 検索画面
- 完全一致(部分文字列一致)検索。入力語を含む日記を新しい順に一覧。
- 結果タップ → その日のエディタへ。

### 2.4 補助:メニュー/設定
- テキスト書き出し(共有シート経由でバックアップ)。
- 購入/復元(買い切り)。
- アプリ情報・プライバシー方針(「データは端末内のみ」)。

## 3. データ設計

### 3.1 モデル
```
DiaryEntry
  - date: DateTime(その日の 0:00、日単位のキー。1日1エントリ)
  - text: String(本文)
  - updatedAt: DateTime(最終更新)
```
- 1日=1エントリ。キーは `yyyy-MM-dd` の文字列(ローカル日付)。
- タイムゾーンは端末ローカル固定。UTC変換で日付がずれないよう、日付キーはローカルの年月日から生成する。

### 3.2 保存方式
- ローカルDBは軽量な組み込みを使う。初期実装は **JSONファイル + 端末内保存**(`path_provider` のアプリ専用ディレクトリ)で開始し、テストしやすい抽象(`DiaryRepository`)で包む。
  - 理由:オフライン完結・依存最小・テスト容易。将来 sqlite / drift に差し替えても UI に影響が出ないよう Repository で隔離する。
- 保存先:アプリのドキュメントディレクトリ内 `diary.json`。
- 設定・購入状態は `shared_preferences`(または同ディレクトリの小さな JSON)。

### 3.3 リポジトリ抽象(テスト対象の中心)
```
abstract class DiaryRepository {
  Future<List<DiaryEntry>> loadAll();
  Future<DiaryEntry?> get(DateTime date);
  Future<void> put(DiaryEntry entry);      // 本文が空なら delete と同義
  Future<void> delete(DateTime date);
  Future<String> exportAsText();            // 書き出し用の連結テキスト
  Future<List<DiaryEntry>> search(String query); // 部分文字列一致
}
```
- 実装:`JsonDiaryRepository`(本番)/ `InMemoryDiaryRepository`(テスト)。
- 日付正規化ユーティリティ `dateKey(DateTime)` を共通化し、境界(月末・うるう年・未来日)をユニットテストで担保。

## 4. 買い切り課金の仕組み

- **無料枠:合計30日分(30エントリ)まで作成可能。** 31件目を保存しようとしたら購入導線を表示。
  - 「30日分」は "直近30日" ではなく "作成したエントリ数の合計" で数える(シンプルで誤解が少ない)。設計上ここは明記する。
- 買い切り(非消費型 / non-consumable)500円で無制限・全機能解放。
- 課金基盤:`in_app_purchase`(Flutter公式)。iOS の StoreKit を利用。**外部サーバーでのレシート検証は行わない**(オフライン方針)。端末側で購入状態を保持し、`in_app_purchase` の復元(restorePurchases)で機種変更に対応。
- 購入状態は `PurchaseStore`(抽象)で隔離。テストではフェイクを使い、UI/制限ロジックを検証する。
  - `bool get isPremium`
  - `Future<void> buy()`
  - `Future<void> restore()`
- 制限の判定は Repository 件数 + PurchaseStore の状態を組み合わせる純粋関数 `canAddNewEntry(count, isPremium)` に集約し、ユニットテストする。
- **注意(要相談事項):** 実際のプロダクトID登録・App Store Connect設定・価格ティア・審査は Mac/外部作業。ここはイシューで相談してから進める。コード上は課金の骨組み(抽象+フェイク+UI)までを先行実装する。

## 5. デザイン方針

雛形っぽさを消す(store-safety.md 対応)。標準部品そのままにしない。

- **配色:** 落ち着いた和のトーン。ベースは生成りの白 / 墨に近いダークグレー。アクセントに季節を感じる一色(藍〜青磁系)。日記のある日はアクセント色の濃淡で「たまっていく」感を出す。ライト/ダーク両対応。
- **タイポ:** 本文は可読性重視。見出しは少しゆったりした字間。日付は数字を主役に大きく。
- **余白:** 詰め込まない。カレンダーのマス目にもゆとり。1画面1目的。
- **モーション:** 書いた瞬間にその日がふわっと色づく等、達成感を小さく演出(過剰にしない)。
- **トーン&マナー:** 誇張しない・急かさない。空の日は責めない表現。
- Material 3 をベースに `ColorScheme` / `TextTheme` をカスタムし、既製感を消す。

## 6. 技術方針

- Flutter(stable)。iOS優先、将来Android対応可能な単一コード。
- 状態管理:初期は軽量に(`ChangeNotifier` + `provider` もしくは標準の `ValueNotifier`)。過剰な依存を避ける。
- 依存は最小限:`path_provider`、`shared_preferences`、`in_app_purchase`、`intl`(日付整形)、テストは標準 `flutter_test`。
- **オフライン完結:** ネットワーク通信を行うコードを持たない(課金の StoreKit を除く)。

## 7. テスト方針(ループエンジニアリングの合否)

- `flutter analyze` 警告ゼロ。
- ユニットテスト中心(UIに依存しないロジックを厚く):
  - `dateKey` の境界(月末・うるう年・タイムゾーン非依存)。
  - `InMemoryDiaryRepository` の put/get/delete/search/export。
  - 無料枠制限 `canAddNewEntry` の分岐。
  - 検索の部分一致・大文字小文字・空クエリ。
- ウィジェットテスト:カレンダー描画・エディタ保存・購入導線の表示条件(段階的に追加)。
